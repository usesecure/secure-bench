# Phase 19 frozen multi-scanner holdout

Phase 19 is a prospective, scanner-neutral examination frozen before any scanner execution. It authors 56 structural vulnerable/control pairs—112 opaque cases—over taxonomy 1.0.0 families SE1001 through SE1007 and authoritative Evidence Contract v2 semantics. It does not produce results, scores, rankings, superiority claims, production-readiness claims, or complete-coverage claims.

## Corpus design

Every family has eight pairs. Node, Express, Next.js App Router, and Server Actions each have fourteen pairs; JavaScript, JSX, TypeScript, and TSX each have fourteen; direct, helper-mediated, inter-file aliased, and control-flow-sensitive topologies each have fourteen. Every family-by-factor cell is exactly two. Every cell of the three 4×4 framework/format/topology intersections is either three or four, the mathematical optimum for 56 pairs. Vulnerable/control ordering is counterbalanced 28/28.

Pairs differ in exactly one declared file through an exact bidirectional mutation. They retain the same candidate value, protected resource, source kind, and sensitive-operation family. Vulnerable cases retain a connected realizable source-to-sink path. Controls use resource-bound authorization, fixed executable arrays, fixed operation maps, canonical filesystem confinement, exact outbound or redirect origins, or SQL parameterization. Ten path-relevant adversarial variants cover misleading names/comments, aliases, destructuring, wrappers, blocklists, suffix tricks, mutable allowlists, non-dominating guards, caught exceptions, and ambiguous helpers.

Case paths and source text contain no classification, taxonomy, CWE, expectation, or scanner labels. Ordering is the SHA-256 sort of the committed seed and pre-randomization coordinates, followed by opaque sequential IDs and alternating orientation. Reconstruction produces every committed byte from public frozen inputs.

## Evidence and commitments

Each case embeds an Evidence Contract v2 object validated against the unchanged Phase 16 schema. Spans are byte- and line-checked against the exact fixture, all declared edges are connected, vulnerable paths have no effective barrier, and controls declare the dominating authorization, rejection, confinement, allowlist, separation, or parameterization effect.

The manifest freezes the aggregate corpus SHA-256 and the Merkle root of all 112 canonical evidence contracts. Commitments additionally bind the seed, manifest, provenance, three execution contracts, public rules, balance tables, and overlap report. `SHA256SUMS` covers generated fixtures and metadata plus frozen Phase 19 bindings, execution contracts, schemas, rules, methodology, and provenance. The single append-only genesis entry records `holdout_frozen` and `genesis-no-execution`; no run entry exists.

Normalized seven-token shingle comparison rejects exact normalized duplicates and excessive cross-pair or historical overlap. Public corpora through Phase 12 plus disclosed Phase 17/18 conformance sources are compared. Phase 13/14 material is deliberately not read or consumed; its immutability is inherited from the exact Phase 18 base tree.

## Future execution contracts

Secure Engine is fixed to the official 0.1.6 RPM and extracted CLI hashes in the immutable binding. OpenGrep is fixed to the official 1.22.0 Linux x86_64 binary and Phase 17 adapter. Semgrep CE is fixed to the 1.170.0 wheel, Python 3.14.6 runtime identity, 66-wheel closure, dependency lock, and Phase 18 OSS-only adapter.

The native lane is available only for Secure Engine's built-in analysis. OpenGrep has no eligible maintained offline native ruleset, and Semgrep CE has no offline built-in default security ruleset, so those native lanes are explicitly unsupported. The public capability-normalized rules are available to OpenGrep and Semgrep CE. Secure Engine 0.1.6 exposes no frozen public external-rule interface, so its normalized lane is explicitly unsupported. Unsupported means unavailable—not failure, partial credit, or invented evidence.

Every available command uses one isolated read-only case copy, a network namespace, a read-only host root, bounded output/time/memory/process limits, disabled version probes, cleared proxy/provider/token variables, and no AI or credentials. Process-status adjudication remains separate from finding adaptation. Native and normalized results may never share a denominator, aggregate, headline score, or rank.

## Verification boundary

The Rust verifier validates schemas, exact static hashes, balance, mutations and inverses, file sets, paths, spans, value connectivity, barrier semantics, privacy, provenance, duplicate and overlap limits, commitments, Merkle reconstruction, checksums, and the genesis chain. The gate reconstructs twice and compares outputs, checks the original Secure Engine binding bytes, enforces historical diff scope, performs process/source audits, and runs formatting, strict Clippy, offline tests, RustSec without fetching, and cargo-deny.

Static fixtures are intentionally bounded models of framework entrypoints. No scanner output exists in Phase 19, and no statement about future scanner performance can be inferred from the freeze.
